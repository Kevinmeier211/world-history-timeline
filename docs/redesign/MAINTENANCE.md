# Maintenance and release handoff

This is a procedure, not an enabled automation. The protected November 1 release is a historical restoration reference, not an approved automatic rollback target; the limitations below govern any restoration decision. Retain its `output/vercel-living-timeline-2026-11-01` artifact manifest, static staging directory, authenticated deployment record and served-download hashes in the release archive.

Content authoring uses the eight chapter files, shared records and source registry in `scripts/redesign/content-canonical/`. Find each record's file in `docs/redesign/CONTENT-OWNERSHIP.json`. Adding a record also requires its owner and ordered ID in `content-canonical/manifest.json`. The historical base and transformation pipeline are retained for provenance and comparison. Make current corrections in the canonical owner file.

For an intentional content change, run `npm run content:build`, refresh ownership with `node --import tsx scripts/completion/content-ownership.ts` through the resource launcher, and record the new corpus hash with the editorial rationale. Current delivery and citation contracts govern that revision. Set `ATLAS_BASELINE_CORPUS` only when a structural refactor must preserve a particular frozen corpus byte for byte. The November 5 migration baseline remains historical evidence.

After every content change, regenerate content and inventories, run the complete data/citation contract, inspect the affected claim/source locators, review changed images and rights, and rerun affected reading, search, comparison, activity and print flows. A change to a source URL or quotation requires actual source consultation. A metadata refresh alone does not establish that an old interpretation remains supported.

After every application change, run types/lint and the current-atlas tests, then the relevant browser contracts. Notebook, navigation and storage changes require the concurrency/recovery matrix in Chromium, Firefox and WebKit. Dependency updates require a clean locked install and the complete candidate suite. Never raise a performance or accessibility threshold to make a failing result pass without an explicit reviewed decision.

Before a release, create a new source/build/asset hash manifest, preserve exported notebook fixtures and a version-1 compatibility receipt, complete the required PDF/portable checks, and reconcile the human review register with the exact content revision. Stage only the intended static application and hosting configuration. Preserve the existing sign-in protection. Verify served bytes for the application/data samples and every downloadable artifact; deployment metadata is insufficient.

For restoration, verify the exact artifact and its current limitations before choosing a target. The [November 5 local rehearsal](review/ROLLBACK-REHEARSAL-2026-11-05.md) found that the November 1 production artifact restores two archive scans with unresolved redistribution scope and older notebook safeguards; it is not suitable for automatic rollback. The identified forward-restoration package preserves the current protections but is a local, undeployed review candidate. Provider restoration still requires approval and fresh project/access verification. Verify old and new notebook exports against the prior reader; the current persistence work deliberately retains version 1 but introduces alternative notes and revisions that must remain inspectable. Preserve browser data and export a backup before any migration; do not rely on deployment rollback to roll back local browser storage. The same-origin local compatibility rehearsal passed with synthetic data; provider preview/rollback execution remains pending.

Monthly, review source-link/status changes and source availability. Classify failures as removed, redirected, access-denied, rate-limited or indeterminate; do not automatically rewrite historical claims or delete sources because a request fails. Escalate consequential changed claims to editorial review. Record checked date, actual URL, response category, source ID, interpretation affected and resolution.

Quarterly, sample one case from each chapter, two comparisons, two investigations, a fresh notebook export/import and one PDF/portable extraction. Rotate regions and evidence types. Review the finite gap register separately from new expansion ideas. A new historical topic or feature goes into a scoped backlog; it does not silently enlarge an already accepted release.

Owner handoff must identify the current implementation owner, the actual independent reviewers and their bounded scopes, the person responsible for physical-device/print checks, and Kevin's release decision. Unassigned roles and missed checks remain visible as pending work.
